# ADR-059: 规划步骤必须传入全部已知行程条件

Family: places-agent planning / LLM prompts.

## Status

**Accepted**（2026-09-09）

## Context

必去提名 L3（`buildNominateMustSeeUserMessage`）只拼了城市、天数、人数、行程类型、预算、节奏、交通。2play 起飞已把日历 `bounds.start` / `bounds.end` 传给 `plan_trip`，agent **没有**把日期（以及当时已有的起点名、用户必去、其他要求）写入提名提示。

后果：名单与出行月份脱节（例如夏季行程仍可能提名「断桥残雪」）。这不是模型「不懂季节」，而是**调用方已知条件被实现丢掉**。

同类风险：任何规划 LLM / 工具步若只传子集，都会出现「产品已收集、智能体没看见」。

## Decision

### D1 — 已知则必传

对每一次规划相关的模型调用或内部规划函数（提名、骨架、填站、贴士、改行程等）：

1. 以**该步执行时 Trip / `plan_trip` 入参上已有、非空的条件**为全集。
2. 这些条件必须进入该步的 user/system 可见上下文（L3 参数行或等价结构化入参）。
3. **禁止**因「提示要短」「芯片还没出」「日期只用来算天数」而省略已有字段。
4. 尚未收集的条件（用户还没答、已跳过且无默认）可以不出现；不得编造。

提名步当前已知全集至少包括：`city`、`numDays`、`bounds`、`party_size`、`trip_type`、`budget`、`pace`、`transit_preference`、已有 `origin.name`、已有 `must_include`、已有自由文本 `other`。日后起飞或续跑新增字段，默认加入全集，除非另有 ADR 明示排除。

### D2 — 传入不等于验收

传入是硬要求。模型仍可能忽略软约束。硬闸仍是 L0（落点、合格景点、族去重）。不得用「模型应该自己知道夏天」代替传日期。

### D3 — 不写城市季节表

用日期/月份让模型判断时令。禁止为「夏天杭州不出现断桥残雪」在源码里维护城×季节 POI 表（ADR-042）。

### D4 — 坐标与供应商身份仍不进 L3

PlaceCard / transit **字段表**、`native_id`、坐标仍不进提名 user 消息（L0/L1）。D1 管的是**行程约束**，不是把地图卡 schema 贴进提示。

## Rationale

- 只加季节启发式、不传日期：仍漏跨月行程，且难测。
- 只信 `numDays`：3 天可以是 1 月或 7 月。
- 城表挡季节名：违反 ADR-042，且不可扩展。

## Consequences

- `nominateMustSeeViaLlm` / `discover_places` 提名必须转发 `bounds` 及当时已有的起点、必去、其他要求。
- 新增规划提示时，对照 D1 做清单测试（有则出现、无则省略）。
- 续跑 `plan_trip` 时，后问到的条件进入后续步骤的提示/入参。
- 选芯片前 8 的热度/多样性（方案 B/C）正交，不替代本 ADR。
